# Architectural Assumptions & Design Decisions

This document records architectural decisions, assumptions, and configurations made during the development of the GUtech Internal LMS according to the AI Build Specification.

## 1. Monorepo & Directory Structure
- The project follows a clean decoupled structure with:
  - `frontend/`: React 18+ / Vite + TypeScript + Tailwind CSS + Lucide Icons + TanStack Query + React Router v6.
  - `backend/`: Node.js 20+ / Express + TypeScript + Zod + Helmet + Pino + Multer + Vitest + Supertest.
  - `supabase/`: Ordered migration files (`0001` - `0006`), `seed.sql`, and `config.toml`.
- Root `package.json` uses npm workspaces (`frontend`, `backend`) with unified scripts (`npm run dev`, `npm run build`, `npm run test`).

## 2. Authentication & Authorization
- Supabase Auth handles identity and tokens; public sign-up is completely disabled.
- Users are created by Admin via `/api/admin/users`.
- Role verification (`admin`, `teacher`, `student`) is strictly validated server-side in Express middleware (`requireAuth`, `requireRole`) and enforced in Supabase RLS.
- Deactivated users (`is_active = false`) are immediately rejected upon auth middleware check.
- When `must_change_password` is true, the user is required to update their password.

## 3. Storage & Signed URLs
- Private Supabase Storage buckets: `resources`, `submissions`, `complaint-attachments`.
- All downloads are served via expiring 60-second signed URLs generated by the backend API.
- File upload constraints:
  - Resources: max 25 MB (allowed MIME: PDF, DOCX, PPTX, images, ZIP).
  - Submissions & Complaints: max 10 MB.
  - MIME types and file extensions are verified server-side.

## 4. Assessment & Auto-Grading Engine
- Quizzes support `mcq_single`, `mcq_multi`, and `true_false`.
- Correct answers live in the separate `quiz_answers` table with teacher/admin-only RLS; they are never exposed to students in API responses.
- Auto-grading runs server-side upon submit. Multi-select questions are evaluated as all-or-nothing per specification.
- Time limit enforcement compares `now() <= started_at + (time_limit_minutes * 60s) + 10s grace`. Submissions after this threshold are rejected or auto-submitted with 0 for unanswered.
- Single attempt per student is strictly enforced.
- Assignment lateness is determined strictly by the server (`now() > due_at`). If `allow_late` is false, submissions post-deadline return HTTP 409 Conflict. Resubmissions reset prior marks/grading.

## 5. Dual-Mode Database Adapter (Supabase & Resilient Fallback)
- The user will provide Supabase keys after initial scaffold.
- The backend features a layered architecture (`routes` -> `controllers` -> `services` -> `repositories`).
- Repositories connect to Supabase PostgreSQL when credentials (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) are present.
- In test mode or when mock credentials are supplied, an in-memory repository store seeded with the full sample dataset (`supabase/seed.sql`) is utilized. This enables test execution, rapid local frontend prototyping, and seamless switchover to live Supabase once API keys are added.

## 6. Realtime Communication & Chat
- Classroom chat is restricted to course members (enrolled students and assigned teachers).
- Rate-limited to 20 messages per minute per user.
- HTML input is sanitized; messages render safely as text (no XSS).
- Soft delete (`deleted_at`) is supported within 5 minutes for senders, or anytime for teachers/admins.
- Realtime events are handled via Supabase Realtime channel subscriptions with optimistic UI updates in React.

## 7. Responsiveness & UI/UX
- Mobile-first responsive design catering down to 360px viewport width.
- Unique academic palette: GUtech Deep Slate (`#0B132B`, `#1C2541`), Academic Emerald (`#059669`, `#10B981`), Indigo highlights, warm pearl neutral surfaces, WCAG AA compliant contrast.
- Includes dedicated User Profile view with profile details, student roll number, role badges, and in-app password update dialog.
